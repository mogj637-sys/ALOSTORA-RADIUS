# خطة استيراد ومزامنة MikroTik User Manager

**الحالة:** متطلب معتمد؛ التنفيذ المرحلي والتحقق الفعلي ما زالا مطلوبين. اتصال User Manager يتم إلى عنوان IP/اسم المضيف والمنفذ الذي يحدده المشغّل داخل الشبكة المحلية، ولا يفترض أن الخدمة موجودة على RB2011 أو على راوتر بعينه.

## الهدف
نقل الكروت الموجودة حالياً في MikroTik User Manager إلى قائمة كروت ALOSTORA-RADIUS الموحدة، مع ما يمكن قراءته والتحقق منه من الباقات والحدود والحالات والجلسات والاستخدام، ثم دعم مزامنة مستمرة أثناء الانتقال.

## النطاق الأول
- يبدأ دعم الموصل بـ RouterOS v6؛ الجهاز المستهدف يحدده المستخدم من عنوان الإدارة والمنفذ المسجلين، ولا يرتبط بطراز أو راوتر محدد.
- RouterOS API العادي أو API-SSL حسب إعداد الجهاز.
- قراءة User Manager فقط، دون تعديل بيانات المصدر.
- استيراد المستخدمين والبروفايلات والقيود والجلسات والإحصائيات المتاحة.
- لا يتم اعتبار دعم RouterOS v7 متحققاً حتى يختبر adapter الخاص به.

## رحلة المستخدم في الواجهة
1. يختار الراوتر المسجل من إدارة MikroTik.
2. تظهر حالة بيانات API: جاهزة أو غير مكتملة. يجب أن تكون بيانات API محفوظة مسبقاً ومشفرة؛ لا تعرض كلمة المرور.
3. يضغط «اختبار الاتصال» ليتحقق النظام من الوصول والمصادقة وإصدار RouterOS ووجود User Manager.
4. يضغط «فحص بيانات User Manager» لجلب ملخص قراءة فقط.
4.1 يمكن للمشغّل اختبار قراءة سجل واحد بإدخال اسم مستخدم محدد عبر endpoint التشخيص؛ ينفذ RouterOS exact-match query ويطلب قائمة حقول صغيرة لا تتضمن كلمة المرور. هذه أداة تحقق وليست معاينة جماعية أو استيراداً.
5. تعرض المعاينة عدد المستخدمين والبروفايلات والقيود والجلسات والعدادات، وتقسم الكروت إلى جديد ومكرر ومتعارض وبيانات ناقصة.
6. يراجع ربط الباقات والسرعات. لا تُستورد الأسعار والعمولات ونقاط البيع من تخمين.
7. يعتمد «الاستيراد الأولي» بعد المراجعة. بعده يمكن تفعيل المزامنة المستمرة وتحديد فاصلها.
8. تعرض شاشة السجل كل تشغيل ونتيجته والدفعة التي وصل إليها والتحذيرات والأخطاء.

## إعدادات الاتصال
- Host: يستخدم عنوان الإدارة المسجل للراوتر.
- Port: api_port المسجل، مع تمييز API العادي عن API-SSL وفق إعداد الراوتر.
- Username/Password: من حقول API المشفرة الموجودة في سجل Router.
- Timeout: محدود وقابل للضبط؛ لا يسمح بطلب API غير محدود.
- Permissions: حساب مخصص بأقل صلاحيات قراءة لازمة. لا تستخدم حساب full إذا أمكن تجنب ذلك.
- Network: يسمح بالاتصال من خادم ALOSTORA إلى الراوتر عبر شبكة الإدارة/VPN فقط؛ لا يفتح API على الإنترنت العام.

## استراتيجية البيانات

### المستخدمون والكروت
- مفتاح التطابق الأساسي هو هوية المصدر + معرف User Manager الأصلي.
- username يحفظ كاسم دخول، لكن لا يكفي وحده لتمييز السجل المستورد عن سجلات مصدر آخر.
- يحفظ رقم/معرف User Manager الأصلي وبيانات البروفايل والحدود والحقول الخام في سجل مصدر قابل للتدقيق.
- عند تكرار username موجود في ALOSTORA، يصنف السجل كتعارض للمراجعة ولا يُدمج أو يستبدل تلقائياً.
- لا يُنشأ بيع جديد أو حركة POS أو عمولة للكرت المستورد.

### بيانات الاعتماد
- لا بد من اختبار ما يعيده RouterOS API فعلياً لـ User Manager user. لا نفترض أن كلمة المرور قابلة للقراءة.
- إذا أعاد المصدر كلمة مرور صريحة عبر قناة API محمية وبصلاحية قراءة مناسبة، تشفر فوراً بمفتاح CREDENTIAL_ENCRYPTION_KEY ولا تُسجل في logs أو تقارير المعاينة.
- إذا أعاد hash/verifier، لا يُقبل إلا إذا كانت صيغة التحقق مدعومة مباشرة في مصادقة RADIUS الحالية وتم اختبارها. خلاف ذلك يوضع الكرت في حالة تحتاج معالجة اعتماد ولا يسمح بالمصادقة.
- لا تنشأ كلمة مرور بديلة تلقائياً ولا يُعرض سر غير موثوق للمستخدم.

### الباقات والحدود
- تُقرأ profiles وlimitations كما هي، وتُعرض خريطة ربط مع خطط ALOSTORA.
- حدود NULL تعني غير محدد/مفتوح فقط بعد فهم دلالة المصدر. الصفر لا يحول إلى NULL دون معرفة موثوقة.
- تحفظ أسماء السرعات الأصلية، ولا تُفترض مطابقتها لسرعات النظام الجديد.
- إذا اختلفت دلالة حد الوقت أو الصلاحية بين النظامين، تظهر حالة تحتاج مراجعة ولا يُجرى تحويل صامت.

### الجلسات والاستخدام
- استيراد الجلسات التاريخية لا يجعلها نشطة في ALOSTORA.
- حفظ معرف الجلسة الأصلي ووقت البداية والنهاية ومدة الاتصال وIP وMAC وNAS عندما تكون متاحة.
- حفظ upload/download كل على حدة، والتحقق من وحدات العداد ومعناه.
- إذا لم يوفر المصدر معرف جلسة ثابتاً، تحفظ الجلسة كسجل تاريخي مرتبط بمعرف مصدر مركب موثق، أو تستبعد مع تقرير واضح إذا تعذر منع التكرار.
- في المزامنة المستمرة تحفظ آخر لقطة عدادات لكل سجل مصدر؛ يضاف الفرق الموجب فقط. إعادة اللقطة نفسها لا تضيف استخداماً جديداً. تناقص العداد أو reset يحتاج reconciliation ولا يعالج بطرح سالب.

## مراحل المزامنة وحالاتها
- pending: لم تبدأ.
- connecting: اختبار الاتصال.
- scanning: قراءة المصدر.
- preview_ready: المعاينة جاهزة.
- importing: كتابة دفعة في النظام الجديد.
- syncing: مزامنة فروقات لاحقة.
- completed: اكتملت دون أخطاء مانعة.
- completed_with_warnings: اكتملت مع سجلات غير متاحة أو تحتاج مراجعة.
- failed: فشلت مع حفظ checkpoint وسبب الفشل.
- cancelled: أوقفها المشغل؛ لا تلغي البيانات التي استوردت بنجاح.

كل دفعة تحفظ عدادات discovered/created/skipped/conflicted/failed، وتستأنف من checkpoint بعد فحص idempotency keys.

## قواعد cutover
- لا تشغل المصدرين كجهتي كتابة ومصادقة متوازيتين لنفس الكرت دون قرار صريح.
- قبل cutover: أوقف إنشاء/تعديل الكروت في المصدر القديم أو حدد نافذة تجميد واضحة.
- خذ snapshot جديداً ثم نفذ المزامنة النهائية، وطابق المستخدمين والجلسات ومجاميع الوقت والرفع والتنزيل.
- لا تحذف أو تعطل User Manager بعد النقل. يحتفظ به كمرجع حتى اكتمال فترة التحقق والقبول.
- حوّل راوتراً واحداً في كل مرة، واحتفظ بخطة رجوع موثقة.

## المخاطر التي يجب اختبارها ميدانياً
1. صلاحية API في جهاز User Manager المحدد بعنوان IP والمنفذ لقراءة users/profiles/limitations/sessions/user stats.
2. هل password field قابل للقراءة؟ وما الصيغة التي يعيدها؟
3. الحقول التي تميز الجلسات وتربطها براوتر NAS عند مشاركة User Manager.
4. معنى عدادات bytes/time وهل هي تراكميّة أم per-session أم per-user.
5. طريقة pagination/print وقيود حجم النتائج على جهاز 128MB RAM. توثيق MikroTik الرسمي لـ RouterOS API يثبت أن أمر print يقبل query words للمطابقة والتصفية، ويدعم .proplist لتحديد الحقول، كما يوضح أن Regular Expressions غير مدعومة في API. لكنه لا يوثق معاملي offset/limit عامّين لأمر print؛ لذلك لا يجوز افتراض أن from/count يحققان صفحات محدودة عبر API. يمكن دراسة تقسيم النتائج إلى نطاقات باستخدام مقارنات query (مثل < و>)، لكن ذلك ليس pagination مثبتاً ولا ضماناً لحد أعلى لحجم كل رد؛ يجب اختبار صياغة الاستعلام، ترتيب المقارنة النصية، وعدم التداخل/الفقد على جهاز RouterOS v6.49.23 وببيانات اختبار قبل السماح بالتنزيل. إلى أن ينجح هذا الاختبار، يظل جلب سجلات المستخدمين متوقفاً ولا يستخدم get() غير المحدود.
   - مرجع API: https://help.mikrotik.com/docs/spaces/ROS/pages/47579160/API
   - مرجع User Manager: https://help.mikrotik.com/docs/spaces/ROS/pages/2555940/User%2BManager
   - تنبيه توافق: مسارات User Manager تختلف بين الإصدارات؛ مسارات RouterOS v6 القديمة تبدأ بـ /tool/user-manager، بينما الوثائق الحالية تعرض /user-manager. لا يتم تبديل المسارات أو إعلان دعم v7 دون موصل واختبارات مستقلة.
6. اختلافات RouterOS v7 ونسخ User Manager.

## معايير إيقاف آمنة
- لا يبدأ الاستيراد إذا فشل الاتصال أو لم يتعرف النظام على إصدار User Manager.
- لا يبدأ إذا لم يمكن تحديد مصدر ومفتاح idempotency لكل سجل.
- لا تستبدل أي كرت موجود مسبقاً تلقائياً.
- لا تفعل مزامنة مستمرة إذا لم يمكن تمييز snapshot جديد عن السابق أو إذا كانت العدادات غير مفهومة.
- لا تنفذ cutover إذا كانت كلمات مرور نسبة من الكروت غير قابلة للتحقق أو كانت المجاميع غير متطابقة دون خطة معالجة معتمدة.

## اعتماد نطاق النقل الكامل
اعتمد المشغّل نقل **كل ما يستطيع User Manager المصدر إتاحته فعلياً** إلى ALOSTORA-RADIUS، وليس أسماء المستخدمين فقط. يشمل نطاق الترحيل:

- جميع المستخدمين/الكروت ومعرفات المصدر وأسماء الدخول وحالة التعطيل والعميل وعدد المشاركات.
- بيانات الاعتماد: محاولة قراءة حقل كلمة المرور فقط في اختبار تشخيصي محدود وعلى اتصال محمي. إذا أعاد المصدر كلمة مرور صريحة، تُشفّر فوراً بمفتاح تشفير بيانات اعتماد الكروت قبل التخزين، ولا تظهر في API أو الواجهة أو المعاينة أو السجلات. إذا أعاد المصدر hash أو verifier، فلا يُستخدم إلا بعد إثبات توافقه مع آلية مصادقة RADIUS؛ وإلا يصنف الاعتماد بأنه غير قابل للنقل المباشر وتوضع له معالجة آمنة.
- كل profiles وlimitations وروابطها، validity وstarts-when والأسعار والتعليقات وحدود الوقت والحجم والسرعات.
- حالة كل كرت وتواريخ الإنشاء/أول استخدام/آخر ظهور/الانتهاء والعدادات الحالية والمتبقية متى كانت حقول المصدر متاحة.
- الجلسات النشطة والتاريخية مع معرفاتها وأوقاتها ومددها وعناوين IP/MAC وNAS وعدادات الرفع والتنزيل متى كانت متاحة.
- حفظ لقطة مصدر خام منقحة من الأسرار، مع حفظ القيم الأصلية ووحداتها وعدم تحويل المجهول إلى صفر.
- حفظ أي حقول إضافية غير معروفة حالياً في مساحة بيانات مصدر آمنة ومنقحة، بدلاً من إسقاطها بصمت.

**حدود مهمة:** User Manager ليس بالضرورة نظام مبيعات أو نقطة بيع؛ لذلك لا تُخترع سجلات بيع أو عمولات أو اسم نقطة بيع أو سعر بيع إذا لم تكن هذه المعلومات موجودة في المصدر. تُنقل فقط البيانات التي يقدمها المصدر، وتُعلّم البيانات غير المتاحة أو غير القابلة للتحقق صراحةً.

### أسلوب القراءة وحماية الراوتر
- القراءة الجماعية ستكون عملية ترحيل خلفية مستقلة ذات checkpoint، وليست إعادة قراءة كاملة لجميع الكروت كل دورة.
- يضبط المشغّل دورة عمل القراءة/استئنافها ضمن مجال 1 إلى 7 دقائق؛ وتُنفذ داخل كل دورة دفعات صغيرة بحد أقصى للسجلات والطلبات والوقت، مع تأخير بين الدفعات وإيقاف تلقائي عند الأخطاء أو ارتفاع زمن الاستجابة.
- لا يبدأ تنزيل قائمة المستخدمين كاملة قبل إثبات طريقة تقسيم محدودة النتائج على جهاز RouterOS v6 الفعلي؛ لا يستخدم print/get غير محدود ولا تُفترض معاملات offset/limit.
- تُقرأ الجلسات النشطة والتاريخية بمسارين منفصلين؛ لا تعتبر الجلسات التاريخية جلسات نشطة عند إنشاء سجلات النظام الجديد.
- لا تنفذ أي كتابة أو حذف أو تعطيل أو reboot على الراوتر. القراءة فقط تقلل المخاطر لكنها لا تعني انعدام الحمل؛ لذلك تُراقب CPU/الذاكرة وزمن API، وتُوقف المهمة إذا تجاوزت حدود الأمان.
- لا تتطلب هذه الموافقة اتصالاً فعلياً بالراوتر الآن؛ الاختبار الميداني لا يتم إلا بعد تحديد الجهاز وعنوانه ومنفذه واعتماد نافذة اختبار مناسبة.
