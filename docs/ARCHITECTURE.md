# المعمارية التقنية – ALOSTORA-RADIUS

## 1. مبدأ التصميم
نظام مستقل، مقسم إلى وحدات واضحة. واجهة الويب لا تتصل مباشرة بقاعدة البيانات أو الراوترات؛ جميع العمليات تمر عبر Backend API وخدمات داخلية ذات صلاحيات محددة.

## 2. المكونات
- **FreeRADIUS:** يتعامل مع طلبات Access-Request وAccounting-Request، ويستخدم `rlm_rest` للاتصال بواجهات RADIUS الداخلية في Backend. هذا الاختيار يحافظ على تشفير كلمات مرور الكروت في قاعدة البيانات ولا يتطلب تخزينها كنص مكشوف في جداول SQL الخاصة بـ FreeRADIUS.
- **Backend API (FastAPI):** إدارة المستخدمين والأدوار والكروت والباقات والراوترات ونقاط البيع والتقارير، مع واجهات داخلية محمية لمصادقة RADIUS والمحاسبة.
- **PostgreSQL:** مصدر الحقيقة للبيانات التشغيلية، وحركات المخزون، والعمولات، والجلسات، والتدقيق.
- **Worker:** تنفيذ المهام الخلفية مثل فحص الحدود، إعادة المحاولة لطلبات الفصل، الأرشفة والتقارير.
- **RouterOS API adapter:** اختبار اتصال الراوتر وجلب المعلومات المطلوبة وتنفيذ العمليات المصرح بها. يجب عزل أخطاء الاتصال وعدم تعطيل المصادقة بسبب تعذر API.
- **React UI:** لوحة عربية RTL، وصفحة عميل منفصلة بواجهات محدودة.

## 3. قرارات بيانات أساسية
- الحدود المفتوحة تمثل بـ NULL، وليس صفر.
- تخزين القيم المالية بوحدات نقدية دقيقة (NUMERIC)، لا أعداد عشرية عائمة.
- تخزين الحجم بوحدة bytes والوقت بوحدة seconds مع عرض وحدات مناسبة في الواجهة.
- كل كرت له معرف داخلي ثابت ورقم تسلسلي فريد، واسم مستخدم فريد ضمن نطاق النظام.
- حفظ snapshots لقيمة الباقة والعمولة عند إنشاء/بيع الكرت حتى لا تتغير العمليات القديمة عند تعديل الإعدادات.
- فصل حالات الكرت عن أحداثه: الإنشاء، الطباعة، التسليم إلى نقطة البيع، البيع/التحميل المالي، أول استخدام، الجلسات، الانتهاء، الإلغاء والأرشفة.
- تسجيل المحاسبة بمفتاح جلسة RADIUS ومعالجة Interim-Update بصورة idempotent لمنع مضاعفة العدادات، مع دعم Acct-Input/Output-Gigawords والحزم المتأخرة.
- حفظ عدادات الجلسة التراكمية والفرق بين التحديثات بطريقة تمنع إعادة احتساب البيانات عند وصول تحديث مكرر أو خارج الترتيب.

## 4. قرارات صاحب المشروع المعتمدة
1. **بداية الصلاحية:** تبدأ عند أول استخدام ناجح للكرت.
2. **مدة الصلاحية:** بعد أول استخدام يبدأ عداد مدة الصلاحية بالمرور المتواصل؛ تنتهي الصلاحية بانقضاء المدة حتى لو لم يكن العميل متصلاً.
3. **وقت الاستخدام:** يُستهلك فقط أثناء وجود جلسة اتصال فعالة؛ فترات الانقطاع لا تخصم من رصيد وقت الاستخدام.
4. **الحجم:** الاستهلاك = مجموع التحميل والرفع.
5. **التزامن:** اتصال واحد نشط فقط لكل كرت.
6. **نقطة البيع:** تُحتسب/تُحمّل الكروت على نقطة البيع عند تنفيذ عملية الطباعة الموجهة لتلك النقطة، وليس عند التسليم اليدوي اللاحق.
7. **بيئة التطوير:** يبدأ التطوير والاختبار على Windows 11، مع تصميم قابل للنشر على Linux وWindows 10 وWindows 11.

## 5. دورة حياة الكرت
مسودة حالات: created → printed (اختياري) → allocated_to_pos (عند الطباعة الموجهة لنقطة البيع وتسجيل حركتها) → active/used → exhausted أو expired أو disabled → archived.
يجب ألا تختلط حالة الطباعة بحالة الاستخدام. كل عملية طباعة تُسجل كحدث مستقل. الطباعة الموجهة لنقطة بيع تنشئ حركة مخزون/تحميل واحدة مرتبطة بمعرف عملية طباعة فريد، وتمنع إعادة إرسال الطلب من تكرار الخصم أو الاحتساب. إعادة طباعة نسخة للعميل لا تُنشئ كروتاً ولا تخصم المخزون مرة أخرى؛ يجب التمييز بين طباعة تخصيص لنقطة بيع وإعادة طباعة نسخة.

## 6. حدود الاستخدام والفصل
- يتحقق قرار المصادقة من حالة الكرت والحدود.
- يبدأ انتهاء الصلاحية عند أول استخدام ناجح، ويستمر الوقت التقويمي حتى أثناء عدم الاتصال.
- يُخصم رصيد وقت الاستخدام فقط من مدد الجلسات المتصلة، مع معالجة الجلسات غير المغلقة عند الانقطاع.
- يُجمع التحميل والرفع معاً لحد الحجم.
- عند بلوغ أي حد: منع المصادقات الجديدة، ثم إنشاء طلب Disconnect/CoA إذا كان NAS يدعم ذلك.
- تتبع نتيجة الفصل، مع retry محدود وتسجيل سبب الفشل.
- فرض جلسة واحدة يعتمد على قفل صف الكرت وحجز مصادقة ذري قصير العمر حتى لا ينجح طلبا دخول متزامنان قبل تسجيل Accounting-Start.
- لا نفترض دعم Disconnect/CoA أو تطابق خصائص السرعة بين RouterOS v6 وv7 قبل اختبار فعلي.

## 7. الأمان
- تخزين كلمات مرور الكروت بطريقة آمنة ومتوافقة مع آلية المصادقة المختارة، وعدم تخزينها كنص مكشوف دون ضرورة.
- تشفير أسرار الراوترات، وعدم إظهارها في السجلات أو API responses.
- صلاحيات RBAC مع سجل تدقيق للعمليات الحساسة.
- حماية استعلام العميل من التخمين عبر rate limiting ورسائل خطأ لا تكشف وجود أسماء المستخدمين.
- نسخ احتياطي مع اختبار استعادة دوري.
- أسرار التطوير تحفظ في متغيرات بيئة محلية ولا ترفع إلى Git.

## 8. قابلية التشغيل عبر الأنظمة
- يجب ألا تعتمد الشيفرة الأساسية على مسارات ملفات أو أوامر خاصة بنظام واحد.
- PostgreSQL وAPI والواجهة تُشغّل كخدمات قابلة للحاويات.
- على Linux يمكن تشغيل الخدمات مباشرة أو عبر Docker Engine/Compose.
- على Windows 11 يكون التطوير المحلي عبر Docker Desktop، وتعمل خدمات Linux مثل FreeRADIUS داخل حاوية Linux.
- على Windows 10 يعتمد التشغيل على إصدار Windows 10 المدعوم ومتطلبات Docker Desktop/WSL2؛ وإذا لم تتوفر، يُستخدم Linux VM أو خادم Linux منفصل.
- FreeRADIUS مكون Linux-first؛ لا ندعي وجود تشغيل Windows أصلي مكافئ. سنوفر طريقة تشغيله عبر حاوية Linux/WSL2 على Windows.
- نختبر وثائق التشغيل على الأنظمة المستهدفة قبل إعلان التوافق النهائي.

## 9. الأداء والاعتمادية
- فهارس على username وserial وsession identifiers ووقت الأحداث ومفاتيح التقارير.
- عمليات إنشاء الدفعات تتم على دفعات داخل معاملات قصيرة ومراقبة.
- فصل خدمات الويب وRADIUS والمهام الخلفية لتحديد أثر الأعطال.
- اختبار حمل واقعي لـ 400–500 جلسة متزامنة، مع قياس زمن المصادقة والمحاسبة وتأخر الفصل واستهلاك الموارد.
- لا يعتبر عدد الكروت المخزنة وحده دليلاً على القدرة؛ الحمل الفعلي يتأثر بمعدل المحاسبة والفهارس والعتاد.

## 10. تكامل RADIUS الداخلي المنفذ جزئياً
- `POST /internal/radius/authorize` يتحقق من بيانات الكرت والراوتر، ويثبت أول استخدام والصلاحية، ويحجز الكرت مؤقتاً لمنع دخول متزامن.
- `POST /internal/radius/accounting` يسجل Start وInterim-Update وStop، ويحسب وقت الاتصال فقط ومجموع الرفع والتنزيل، ويتجاهل التكرار ويقاوم الحزم الخارجة عن الترتيب.
- تحمى الواجهات بمفتاح داخلي مستقل `RADIUS_INTERNAL_API_KEY`.
- لا يزال تشغيل FreeRADIUS نفسه، وتوليد قائمة clients من الراوترات، وCoA/Disconnect والاختبار الفعلي على MikroTik غير مكتمل.

## 11. نقاط لم تُحسم بعد
1. مواصفات خادم Linux المستقبلي وموقعه الشبكي بالنسبة للراوترات.
2. عند الطباعة الموجهة لنقطة البيع، هل تُسجل قيمة الكروت كمديونية على نقطة البيع أم تُخصم من رصيد مدفوع مسبقاً؟
3. سياسة إرجاع الكروت غير المباعة من نقطة البيع، وهل يسمح بإرجاع كرت سبق استخدامه؟
4. هل مدة الصلاحية لكل باقة ثابتة (مثلاً 5 أيام) أم يمكن تحديد تاريخ انتهاء تقويمي أيضاً؟

## 12. خطة التحقق
- اختبارات وحدات لبداية الصلاحية من أول دخول، وانقضاء المدة أثناء عدم الاتصال، وتجميع وقت الاتصال فقط، وتجميع التحميل والرفع، ومنع الجلسات المتزامنة.
- اختبارات idempotency لعملية طباعة تخصيص نقطة البيع وإعادة الطباعة.
- اختبارات وحدات للعمولات والحدود وتراكم المحاسبة.
- اختبارات تكامل مع FreeRADIUS وPostgreSQL.
- اختبار فعلي على RouterOS v6 وv7.
- اختبار انقطاع NAS أو RADIUS ثم استعادة المحاسبة.
- اختبار duplicate/out-of-order Accounting packets.
- اختبار ضغط 400–500 اتصال مع معدل Interim-Update محدد.
- اختبار النسخ الاحتياطي والاستعادة قبل الإنتاج.


## 13. استيراد User Manager القديم

### 13.1 الحدود ومصدر الحقيقة
- المزامنة تتم من RouterOS API باتصال صادر من Backend إلى عنوان الإدارة والمنفذ المحفوظين في سجل الراوتر. منفذ API العادي غالباً 8728، وAPI-SSL غالباً 8729 عند تفعيله؛ يجب اختبار إعداد TLS الفعلي وعدم افتراض أن المنفذ وحده يضمن التشفير.
- بيانات API تُفك داخل الخدمة فقط باستخدام ROUTER_SECRET_ENCRYPTION_KEY، ولا تعاد إلى الواجهة ولا تسجل في logs. يستخدم حساب API مخصص بصلاحيات قراءة محدودة.
- أول إصدار يدعم User Manager على RouterOS v6.49.23 كهدف تحقق. يجب اكتشاف إصدار النظام والحزمة والحقول المتاحة قبل تنفيذ أي استيراد. لا تُستخدم أوامر v6 على v7 دون adapter واختبارات مستقلة.
- الاستيراد والمزامنة في المرحلة الأولى قراءة فقط؛ لا حذف ولا تعديل ولا تعطيل على الراوتر القديم.

### 13.2 مراحل العمل
1. **Connection check:** تحقق من الوصول والمصادقة وإصدار RouterOS وتوفر User Manager، مع timeout وحدود للقراءة.
2. **Read-only inventory:** جلب المستخدمين والبروفايلات والقيود والجلسات والإحصائيات على صفحات/دفعات، مع الاحتفاظ بمعرفات المصدر الخام والحقول التي لم تتوفر.
3. **Preview:** تصنيف السجلات إلى جديد وموجود مسبقاً ومتعارض وغير مكتمل، وعرض خرائط الباقات والسرعات المطلوبة قبل اعتماد أي كتابة.
4. **Initial import:** إنشاء سجل مصدر لكل مستخدم، وربطه بكرت واحد في النظام، واستيراد السجلات التاريخية دون إنشاء مبيعات أو حركات نقاط بيع.
5. **Incremental sync:** استخدام checkpoint ومفاتيح المصدر ومقارنة اللقطات؛ تُطبق فروقات العدادات فقط، ولا يُعاد جمع الإجمالي التراكمي عند كل مزامنة.
6. **Cutover:** إيقاف الكتابة على المصدر القديم أو تحديد مصدر الحقيقة بوضوح، والتحقق من الأعداد والمجاميع، ثم تحويل المصادقة إلى FreeRADIUS على دفعات مراقبة.

### 13.3 نموذج المصدر والتطابق
- يجب حفظ هوية المصدر بما يشمل router/source identity ومعرف مستخدم User Manager ومعرف الجلسة الأصلي، لا الاعتماد على username وحده.
- عند مشاركة User Manager بين عدة راوترات، يُستورد المستخدم مرة واحدة وتُربط جلساته بالراوتر الصحيح عند توافر NAS-Identifier أو NAS-IP-Address أو معرّف موثوق آخر.
- لا يُستخدم username وحده لدمج جلسات أجهزة مختلفة. يجب أن يكون مفتاح الجلسة فريداً وثابتاً من المصدر، أو تُحفظ كسجل تاريخي منفصل إذا لم يوفر المصدر معرفاً موثوقاً.
- تحفظ الحقول الخام/غير المفهومة في سجل الاستيراد للمراجعة، ولا تُحوّل تلقائياً إلى حدود أو حالات ذات معنى مختلف.

### 13.4 الاعتمادات والأمان
- بيانات اعتماد User Manager قد لا تكون قابلة للقراءة عبر API أو قد تكون بصيغة لا تتوافق مع مصادقة RADIUS الحالية. لا تُخمن كلمات المرور ولا تخزنها كنص مكشوف. يُعلّم المستخدم بأنه يحتاج إعادة تعيين/معالجة اعتماد إلى أن يُثبت توافق صيغة التحقق.
- يجب ألا ينجح الكرت المستورد بمصادقة غير متحققة. يُحفظ مصدر الاعتماد وحالة التحقق بشكل صريح.
- لا تُعرض API credentials أو RADIUS secrets في استجابات المزامنة أو سجلاتها.

### 13.5 الوقت والحجم والجلسات
- جلسات User Manager القديمة تُستورد كتاريخ، ولا تُنشأ منها جلسات نشطة اصطناعياً.
- يجب توحيد معنى عدادات upload/download قبل تحويلها إلى حقول النظام. يحتفظ النظام بالاتجاهين منفصلين ويحسب إجمالي الاستهلاك كمجموعهما وفق سياسة المشروع.
- عند المزامنة المستمرة، تُقارن العدادات التراكمية مع آخر snapshot مصدر موثوق؛ الزيادة فقط هي التي تُضاف، ويُتعامل مع reset أو rollover أو تناقص العداد كحالة مراجعة لا كقيمة سالبة.
- إذا كانت أوقات أول استخدام أو الانتهاء أو وقت الجلسة غير متاحة أو غير موثوقة، تبقى غير معروفة مع تحذير؛ لا تُنشأ تواريخ افتراضية.

### 13.6 التجارة والتدقيق
- الاستيراد ليس عملية بيع ولا طباعة ولا تخصيص نقطة بيع. لا تُنشأ سجلات pos_inventory_movements أو pos_account_entries أو عمولات للاستيراد.
- تحفظ قيمة السعر ونقطة البيع والعمولة كغير معروفة ما لم توجد بيانات مصدر موثوقة ومراجعة صريحة.
- لكل دفعة سجل تدقيق يتضمن المصدر والراوتر والإصدار ونطاق البيانات وcheckpoint والأعداد والتعارضات والتحذيرات.

### 13.7 اختبارات لازمة قبل التشغيل
- RouterOS v6.49.23 على جهاز الاختبار: استكشاف المسارات والحقول الفعلية لـ user/profile/limitation/session/stats، بما فيها قابلية قراءة كلمات المرور.
- انقطاع الاتصال في منتصف الدفعة ثم الاستئناف دون تكرار.
- مستخدم مكرر بين أكثر من راوتر، وجلسات ذات معرفات متشابهة، وسجلات ناقصة أو خارج الترتيب.
- إعادة مزامنة نفس اللقطة عدة مرات دون تضاعف الأعداد أو الاستهلاك.
- مطابقة المجاميع مع User Manager قبل وبعد الاستيراد.
- اختبار RouterOS v7 مستقل قبل إعلان التوافق.
