# المعمارية التقنية – ALOSTORA-RADIUS

## 1. مبدأ التصميم
نظام مستقل، مقسم إلى وحدات واضحة. واجهة الويب لا تتصل مباشرة بقاعدة البيانات أو الراوترات؛ جميع العمليات تمر عبر Backend API وخدمات داخلية ذات صلاحيات محددة.

## 2. المكونات
- **FreeRADIUS:** يتعامل مع طلبات Access-Request وAccounting-Request، ويقرأ سياسات المصادقة والمحاسبة من PostgreSQL عبر SQL module.
- **Backend API (FastAPI):** إدارة المستخدمين والأدوار والكروت والباقات والراوترات ونقاط البيع والتقارير.
- **PostgreSQL:** مصدر الحقيقة للبيانات التشغيلية، وحركات المخزون، والعمولات، والجلسات، والتدقيق.
- **Worker:** تنفيذ المهام الخلفية مثل فحص الحدود، إعادة المحاولة لطلبات الفصل، الأرشفة والتقارير.
- **RouterOS API adapter:** اختبار اتصال الراوتر وجلب المعلومات المطلوبة وتنفيذ العمليات المصرح بها. يجب عزل أخطاء الاتصال وعدم تعطيل المصادقة بسبب تعذر API.
- **React UI:** لوحة عربية RTL، وصفحة عميل منفصلة بواجهات محدودة.

## 3. قرارات بيانات أساسية
- الحدود المفتوحة تمثل بـ NULL، وليس صفر.
- تخزين القيم المالية بوحدات نقدية دقيقة (NUMERIC)، لا أعداد عشرية عائمة.
- تخزين الحجم بوحدة bytes والوقت بوحدة seconds مع عرض وحدات مناسبة في الواجهة.
- كل كرت له معرف داخلي ثابت ورقم تسلسلي فريد، واسم مستخدم فريد ضمن نطاق النظام.
- حفظ snapshots لقيمة الباقة والعمولة عند إنشاء/بيع الكرت حتى لا تتغير العمليات القديمة عند تعديل الإعدادات.
- فصل حالات الكرت عن أحداثه: الإنشاء، الطباعة، التسليم إلى نقطة البيع، البيع/التحميل المالي، أول استخدام، الجلسات، الانتهاء، الإلغاء والأرشفة.
- تسجيل المحاسبة بمفتاح جلسة RADIUS ومعالجة Interim-Update بصورة idempotent لمنع مضاعفة العدادات.
- حفظ عدادات الجلسة التراكمية والفرق بين التحديثات بطريقة تمنع إعادة احتساب البيانات عند وصول تحديث مكرر أو خارج الترتيب.

## 4. قرارات صاحب المشروع المعتمدة
1. **بداية الصلاحية:** تبدأ عند أول استخدام ناجح للكرت.
2. **مدة الصلاحية:** بعد أول استخدام يبدأ عداد مدة الصلاحية بالمرور المتواصل؛ تنتهي الصلاحية بانقضاء المدة حتى لو لم يكن العميل متصلاً.
3. **وقت الاستخدام:** يُستهلك فقط أثناء وجود جلسة اتصال فعالة؛ فترات الانقطاع لا تخصم من رصيد وقت الاستخدام.
4. **الحجم:** الاستهلاك = مجموع التحميل والرفع.
5. **التزامن:** اتصال واحد نشط فقط لكل كرت.
6. **نقطة البيع:** تُحتسب/تُحمّل الكروت على نقطة البيع عند تنفيذ عملية الطباعة الموجهة لتلك النقطة، وليس عند التسليم اليدوي اللاحق.
7. **بيئة التطوير:** يبدأ التطوير والاختبار على Windows 11، مع تصميم قابل للنشر على Linux وWindows 10 وWindows 11.

## 5. دورة حياة الكرت
مسودة حالات: created → printed (اختياري) → allocated_to_pos (عند الطباعة الموجهة لنقطة البيع وتسجيل حركتها) → active/used → exhausted أو expired أو disabled → archived.
يجب ألا تختلط حالة الطباعة بحالة الاستخدام. كل عملية طباعة تُسجل كحدث مستقل. الطباعة الموجهة لنقطة بيع تنشئ حركة مخزون/تحميل واحدة مرتبطة بمعرف عملية طباعة فريد، وتمنع إعادة إرسال الطلب من تكرار الخصم أو الاحتساب. إعادة طباعة نسخة للعميل لا تُنشئ كروتاً ولا تخصم المخزون مرة أخرى؛ يجب التمييز بين طباعة تخصيص لنقطة بيع وإعادة طباعة نسخة.

## 6. حدود الاستخدام والفصل
- يتحقق قرار المصادقة من حالة الكرت والحدود.
- يبدأ انتهاء الصلاحية عند أول استخدام ناجح، ويستمر الوقت التقويمي حتى أثناء عدم الاتصال.
- يُخصم رصيد وقت الاستخدام فقط من مدد الجلسات المتصلة، مع معالجة الجلسات غير المغلقة عند الانقطاع.
- يُجمع التحميل والرفع معاً لحد الحجم.
- عند بلوغ أي حد: منع المصادقات الجديدة، ثم إنشاء طلب Disconnect/CoA إذا كان NAS يدعم ذلك.
- تتبع نتيجة الفصل، مع retry محدود وتسجيل سبب الفشل.
- فرض جلسة واحدة يحتاج معالجة متزامنة صحيحة (atomic reservation/locking) حتى لا ينجح طلبا دخول متزامنان قبل تسجيل Accounting-Start.
- لا نفترض دعم Disconnect/CoA أو تطابق خصائص السرعة بين RouterOS v6 وv7 قبل اختبار فعلي.

## 7. الأمان
- تخزين كلمات مرور الكروت بطريقة آمنة ومتوافقة مع آلية المصادقة المختارة، وعدم تخزينها كنص مكشوف دون ضرورة.
- تشفير أسرار الراوترات، وعدم إظهارها في السجلات أو API responses.
- صلاحيات RBAC مع سجل تدقيق للعمليات الحساسة.
- حماية استعلام العميل من التخمين عبر rate limiting ورسائل خطأ لا تكشف وجود أسماء المستخدمين.
- نسخ احتياطي مع اختبار استعادة دوري.
- أسرار التطوير تحفظ في متغيرات بيئة محلية ولا ترفع إلى Git.

## 8. قابلية التشغيل عبر الأنظمة
- يجب ألا تعتمد الشيفرة الأساسية على مسارات ملفات أو أوامر خاصة بنظام واحد.
- PostgreSQL وAPI والواجهة تُشغّل كخدمات قابلة للحاويات.
- على Linux يمكن تشغيل الخدمات مباشرة أو عبر Docker Engine/Compose.
- على Windows 11 يكون التطوير المحلي عبر Docker Desktop، وتعمل خدمات Linux مثل FreeRADIUS داخل حاوية Linux.
- على Windows 10 يعتمد التشغيل على إصدار Windows 10 المدعوم ومتطلبات Docker Desktop/WSL2؛ وإذا لم تتوفر، يُستخدم Linux VM أو خادم Linux منفصل.
- FreeRADIUS مكون Linux-first؛ لا ندعي وجود تشغيل Windows أصلي مكافئ. سنوفر طريقة تشغيله عبر حاوية Linux/WSL2 على Windows.
- نختبر وثائق التشغيل على الأنظمة المستهدفة قبل إعلان التوافق النهائي.

## 9. الأداء والاعتمادية
- فهارس على username وserial وsession identifiers ووقت الأحداث ومفاتيح التقارير.
- عمليات إنشاء الدفعات تتم على دفعات داخل معاملات قصيرة ومراقبة.
- فصل خدمات الويب وRADIUS والمهام الخلفية لتحديد أثر الأعطال.
- اختبار حمل واقعي لـ 400–500 جلسة متزامنة، مع قياس زمن المصادقة والمحاسبة وتأخر الفصل واستهلاك الموارد.
- لا يعتبر عدد الكروت المخزنة وحده دليلاً على القدرة؛ الحمل الفعلي يتأثر بمعدل المحاسبة والفهارس والعتاد.

## 10. نقاط لم تُحسم بعد
1. مواصفات خادم Linux المستقبلي وموقعه الشبكي بالنسبة للراوترات.
2. عند الطباعة الموجهة لنقطة البيع، هل تُسجل قيمة الكروت كمديونية على نقطة البيع أم تُخصم من رصيد مدفوع مسبقاً؟
3. سياسة إرجاع الكروت غير المباعة من نقطة البيع، وهل يسمح بإرجاع كرت سبق استخدامه؟
4. هل مدة الصلاحية لكل باقة ثابتة (مثلاً 5 أيام) أم يمكن تحديد تاريخ انتهاء تقويمي أيضاً؟

## 11. خطة التحقق
- اختبارات وحدات لبداية الصلاحية من أول دخول، وانقضاء المدة أثناء عدم الاتصال، وتجميع وقت الاتصال فقط، وتجميع التحميل والرفع، ومنع الجلسات المتزامنة.
- اختبارات idempotency لعملية طباعة تخصيص نقطة البيع وإعادة الطباعة.
- اختبارات وحدات للعمولات والحدود وتراكم المحاسبة.
- اختبارات تكامل مع FreeRADIUS وPostgreSQL.
- اختبار فعلي على RouterOS v6 وv7.
- اختبار انقطاع NAS أو RADIUS ثم استعادة المحاسبة.
- اختبار duplicate/out-of-order Accounting packets.
- اختبار ضغط 400–500 اتصال مع معدل Interim-Update محدد.
- اختبار النسخ الاحتياطي والاستعادة قبل الإنتاج.
