# مرجع المتطلبات الوظيفية

هذا الملف يلخص المتطلبات المستلمة من صاحب المشروع في وثيقة «نص ملصق.txt». الوثيقة الأصلية هي المرجع التفصيلي عند الاختلاف.

## الوحدات
1. لوحة رئيسية وإحصائيات.
2. إدارة الكروت: منفرد/دفعات، ثلاثة أنماط بيانات دخول، توليد أرقام/حروف، منع التكرار، رقم تسلسلي وباركود.
3. الباقات والحدود: قيمة، حجم، وقت، صلاحية، سرعة، قالب طباعة. الحد الفارغ مفتوح ولا يرسل كصفر.
4. السرعات: استيراد أسماء البروفايلات الحقيقية عند الحاجة، دعم اختلافها بين الراوترات، واختبار تطبيقها الفعلي.
5. أجهزة MikroTik: بيانات الربط وNAS-IP-Address والإصدار وحالة الاتصال وإحصائياته.
6. RADIUS: Authentication وAuthorization وAccounting Start/Interim/Stop.
7. الحدود والفصل: منع دخول جديد، ثم Disconnect/CoA عند الدعم، والتحقق وإعادة المحاولة.
8. استعلام العميل: بيانات كرت واحد فقط مع حماية التخمين.
9. نقاط البيع: تسليم واسترجاع ونقل ومخزون وسجل حركة. تُحتسب/تُحمّل الكروت على نقطة البيع عند تنفيذ عملية الطباعة الموجهة إليها.
10. العمولات: مبلغ ثابت أو نسبة، مع تثبيت بيانات العملية التاريخية.
11. قوالب الطباعة: محرر عناصر ومقاسات صفحات وهوامش ومعاينة.
12. التصدير: PDF وTXT وXLSX مع اختيار الحقول.
13. التقارير: المبيعات، المخزون، الطباعة، الأجهزة، الاستخدام والجلسات والفترات.
14. الأرشفة والنسخ الاحتياطي والاستعادة.
15. الموظفون والأدوار وسجل التدقيق.

## قرارات تشغيل الكرت المعتمدة
- تبدأ صلاحية الكرت من أول استخدام ناجح.
- تستمر مدة الصلاحية بعد أول استخدام حتى لو كان العميل غير متصل.
- يحتسب وقت الاستخدام أثناء اتصال العميل فقط، ويتوقف الاستهلاك عند انتهاء الجلسة.
- يحتسب الاستهلاك الحجمي بجمع التحميل والرفع.
- يسمح باتصال واحد متزامن لكل كرت.
- تُحتسب/تُحمّل الكروت على نقطة البيع عند عملية الطباعة الموجهة إليها.

## قواعد تجارية ملزمة
- الكرت المجاني ينشأ منفرداً فقط حسب المتطلبات الحالية، ويستثنى من الإيرادات والمبيعات والعمولات والمخزون التجاري مع الاحتفاظ بسجلاته الفنية.
- إعادة الطباعة لا تنشئ كرتاً ولا تضاعف المخزون.
- يجب التمييز بين طباعة تخصيص الكروت لنقطة بيع وبين إعادة طباعة نسخة؛ الأولى تسجل حركة نقطة البيع مرة واحدة، والثانية لا تكررها.
- التمييز بين الكرت المطبوع والمخصص لنقطة البيع والمستخدم.
- حفظ سجل تاريخي حتى بعد انتهاء الكرت وأرشفته.

## متطلبات الأنظمة
- التطوير والاختبار الأولي على Windows 11.
- قابلية تشغيل التطبيق على Linux وWindows 10 وWindows 11.
- استخدام خدمات قابلة للحاويات وتجنب الاعتماد على مسارات وأوامر خاصة بنظام التشغيل.
- تشغيل FreeRADIUS كخدمة Linux داخل Docker/WSL2 على Windows، مع توثيق المتطلبات الفعلية لكل منصة.
- لا يعلن التوافق النهائي إلا بعد اختبارات تشغيل فعلية على الأنظمة المستهدفة.

## أهداف القبول
- مصادقة RADIUS حقيقية من MikroTik.
- محاسبة دقيقة بلا مضاعفة.
- تطبيق الحدود والسرعات والفصل عملياً.
- صحة المخزون والعمولات واستثناء المجاني.
- دقة PDF وTXT وXLSX.
- سلامة الأرشفة والتقارير والنسخ الاحتياطية.
- اختبار RouterOS v6 وv7 و400–500 اتصال متزامن.
- اختبار idempotency لعمليات تخصيص الطباعة لنقطة البيع وإعادة الطباعة.


## 16. استيراد ومزامنة MikroTik User Manager (متطلب معتمد)
- إضافة وحدة مستقلة باسم «مزامنة User Manager» ضمن إدارة الراوترات، لا تُنشئ قائمة كروت موازية؛ كل كرت مستورد يظهر في قائمة الكروت الرئيسية مع بيان مصدره.
- اختيار الراوتر المسجل وتحديد عنوان الإدارة ومنفذ RouterOS API (8728 أو API-SSL 8729 عند تفعيله)، مع استخدام بيانات API المخزنة مشفرة. لا تُطلب الأسرار عبر المحادثة أو تُعرض بعد الحفظ.
- إنشاء حساب API مخصص بأقل صلاحيات قراءة لازمة، والتحقق من الاتصال وإصدار RouterOS وحزمة User Manager قبل أي قراءة.
- دعم RouterOS v6 User Manager أولاً، واكتشاف اختلافات RouterOS v7 وعدم افتراض تطابق أوامر وحقول الإصدارين.
- توفير معاينة قراءة فقط قبل الاستيراد، تشمل إجمالي المستخدمين والبروفايلات والقيود والجلسات والإحصائيات، والجديد والمكرر والمتعارض والبيانات الناقصة.
- استيراد المستخدمين والبروفايلات والقيود والسرعات والحدود وحالات الكروت وتواريخها والعدادات والجلسات التاريخية والحالية بقدر ما تسمح به واجهة API الفعلية.
- ربط المستخدمين بالباقات الموجودة أو إنشاء اقتراحات ربط للمراجعة؛ لا تُنشأ أسعار أو عمولات أو نقاط بيع أو بيانات طباعة غير موجودة في المصدر.
- الحفاظ على بيانات الاعتماد كما هي فقط إذا أمكن قراءتها أو تحويلها إلى صيغة تحقق متوافقة وآمنة. إذا تعذرت قراءة كلمة المرور أو لم تدعم آلية التحقق الحالية الصيغة المستوردة، يُعلّم الكرت بأنه يحتاج معالجة اعتماد ولا يسمح له بالمصادقة بكلمة مرور مخمّنة.
- مزامنة مستمرة اختيارية بعد الاستيراد الأول، مع checkpoint ومفاتيح مصدر فريدة وعمليات idempotent تمنع مضاعفة الجلسات أو الوقت أو الحجم.
- عدم تحويل الجلسات التاريخية إلى جلسات نشطة. تُستورد كأحداث تاريخية، وتُطابق الجلسات الحالية على معرفاتها ومصدر NAS قبل تحديثها.
- عدم تسجيل الكروت القديمة كمبيعات أو طباعات جديدة، وعدم إنشاء حركات مخزون أو عمولات أو أرصدة نقاط بيع عند الاستيراد.
- عدم حذف أو تعطيل أو تعديل أي مستخدم أو جلسة في User Manager تلقائياً. كل عمليات المرحلة الأولى قراءة فقط.
- تسجيل كل عملية مزامنة: الراوتر والمصدر ووقت البدء والنهاية والنتيجة والأعداد والتحذيرات والأخطاء ومؤشر الاستئناف.
- دعم الإيقاف والاستئناف الآمن، ومعالجة انقطاع الاتصال والدفعات الكبيرة دون تحميل جميع البيانات في الذاكرة.
- قبل التحويل النهائي، اعتماد مصدر حقيقة واحد لكل كرت ومنع التعديلات المتزامنة على النظامين؛ لا تُشغّل مصادقة الكرت نفسه من النظامين معاً دون خطة تحويل صريحة.

### شروط قبول المزامنة
- إعادة تشغيل المعاينة أو المزامنة مرتين لا تضاعف الكروت أو الجلسات أو عدادات الاستخدام.
- تطابق أعداد المستخدمين والبروفايلات والجلسات ومجاميع العدادات مع المصدر ضمن الحقول التي أمكن قراءتها، مع تقرير صريح عن غير المتاح.
- تبقى كل البيانات التجارية غير الموجودة في User Manager غير محددة ولا تدخل التقارير المالية.
- نجاح اختبارات الاستيراد على نسخة بيانات تجريبية ثم RouterOS v6.49.23 الفعلي قبل اعتماد الإنتاج.
- اختبار التوافق مع RouterOS v7 على حدة قبل إعلان دعمه.
