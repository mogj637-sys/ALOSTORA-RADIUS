# الباقات والكروت – API الأولية

جميع المسارات التالية تتطلب رمز JWT لمستخدم يحمل دور `owner`.

## الباقات

### إنشاء باقة
`POST /api/v1/plans`

مثال:

```json
{
  "code": "BASIC-1",
  "name": "الباقة الاقتصادية",
  "price": 100,
  "data_limit_bytes": 1073741824,
  "session_time_limit_seconds": 25200,
  "validity_period_seconds": 604800,
  "speed_profile": "default",
  "description": "1GB و7 ساعات و7 أيام"
}
```

أي حد يترك `null` يكون مفتوحاً. لا تستخدم صفر للتعبير عن الحد المفتوح.

### عرض الباقات
`GET /api/v1/plans`

## الكروت

أنواع تسجيل الدخول:
- `username_only`: اسم مستخدم دون كلمة مرور.
- `same_credentials`: اسم المستخدم وكلمة المرور متطابقان.
- `separate_credentials`: اسم مستخدم وكلمة مرور مختلفان.

أنماط توليد اسم المستخدم:
- `digits`: أرقام فقط.
- `letters`: حروف إنجليزية كبيرة فقط.
- `alphanumeric`: أرقام وحروف إنجليزية كبيرة.

### إنشاء كرت منفرد
`POST /api/v1/cards/single`

```json
{
  "plan_id": 1,
  "username": "12345678",
  "card_type": "same_credentials",
  "is_free": false
}
```

لنوع `separate_credentials` أرسل `password`. للكرت المجاني استخدم `is_free: true`. خيار المجاني متاح للكرت المنفرد فقط.

### إنشاء دفعة
`POST /api/v1/cards/batch`

```json
{
  "plan_id": 1,
  "quantity": 100,
  "card_type": "separate_credentials",
  "generation_mode": "digits",
  "username_length": 8,
  "password_length": 10,
  "prefix": "77"
}
```

الدفعة الحالية تقبل من 1 إلى 5000 كرت. إذا حدث تعارض في أسماء المستخدمين أو فشل الحفظ، لا تحفظ الدفعة جزئياً.

### عرض الكروت
`GET /api/v1/cards?offset=0&limit=50`

يمكن استخدام `status` كمرشح. لا يعيد هذا المسار كلمات المرور أو النص المشفر.

## حماية بيانات الاعتماد
- كلمات مرور الكروت تحفظ مشفرة باستخدام Fernet.
- يجب تعيين `CREDENTIAL_ENCRYPTION_KEY` قبل إنشاء الكروت.
- مفاتيح التشفير لا تحفظ في Git ولا ترسل إلى المتصفح.
- استجابة الإنشاء تعرض كلمة المرور مرة واحدة ليتم حفظها أو طباعتها؛ لا توجد واجهة لاسترجاعها كنص مكشوف.
- خدمة RADIUS لم تُربط بعد بعملية فك التشفير؛ لا تستخدم هذه المرحلة لمصادقة مشتركين حقيقيين.

## تحذير مهم بشأن مفتاح التشفير
يجب الاحتفاظ بنسخة احتياطية آمنة من `CREDENTIAL_ENCRYPTION_KEY` خارج الجهاز والمستودع. فقدان المفتاح يعني تعذر فك تشفير كلمات مرور الكروت المخزنة، وتغيير المفتاح دون خطة ترحيل سيؤثر على بيانات الاعتماد الحالية. لا ترسل هذا المفتاح في المحادثة ولا ترفعه إلى GitHub.


## إدارة الباقات والكروت

### تعديل باقة أو إيقافها
`PATCH /api/v1/plans/{plan_id}`

أرسل الحقول التي تريد تغييرها فقط. مثال إيقاف باقة:

```json
{ "is_active": false }
```

عرض جميع الباقات بما فيها المتوقفة:
`GET /api/v1/plans?include_inactive=true`

### البحث وتصفية الكروت
`GET /api/v1/cards?offset=0&limit=50&search=777&status=generated&plan_id=1&is_free=false`

- `search`: يبحث في اسم المستخدم والرقم التسلسلي.
- `status`: الحالة الحالية للكرت.
- `plan_id`: رقم الباقة.
- `is_free`: حصر النتائج في المجانية أو التجارية.

### تغيير حالة الكرت
`PATCH /api/v1/cards/{card_id}/status`

إيقاف كرت:

```json
{ "action": "suspend" }
```

إعادة تفعيله:

```json
{ "action": "reactivate" }
```

إلغاء كرت لم يبدأ استخدامه:

```json
{ "action": "cancel" }
```

كل تغيير يسجل في `card_events` مع اسم المشرف. لا يحذف الإلغاء سجل الكرت. الإلغاء غير متاح للكرت الذي بدأ استخدامه.

## عمليات الطباعة ونقاط البيع

### تنفيذ طباعة موجهة لنقطة بيع
`POST /api/v1/print-jobs`

```json
{
  "idempotency_key": "print-batch-2026-0001",
  "point_of_sale_id": 1,
  "card_ids": [
    "00000000-0000-0000-0000-000000000001"
  ],
  "template_code": "green-voucher",
  "is_reprint": false
}
```

- يجب أن تكون نقطة البيع موجودة ومفعلة.
- تخصيص الكرت التجاري لنقطة البيع يحدث في معاملة قاعدة بيانات واحدة مع سجل حركة المخزون.
- يتحول الكرت التجاري إلى الحالة `allocated` ويسجل وقت التخصيص.
- الكروت المجانية تظهر في سجل عملية الطباعة، لكنها لا تُخصص تجارياً ولا تنشئ حركة مخزون أو قيمة مالية.
- مفتاح `idempotency_key` يمنع تنفيذ الطلب نفسه مرتين. إذا أعيد المفتاح مع بيانات مختلفة يرجع الخادم تعارضاً.
- استجابة عملية الطباعة المصرح بها تتضمن بيانات الدخول اللازمة لإظهار قسيمة الطباعة، بما فيها كلمة المرور بعد فك تشفيرها داخل الخادم. لا يعيد مسار قائمة الكروت كلمات المرور. تعامل مع استجابة الطباعة كبيانات سرية ولا تحفظها في سجلات المتصفح أو ملفات عامة.

### إعادة طباعة نسخة
أرسل الطلب نفسه مع مفتاح جديد و`is_reprint: true`. يشترط أن تكون الكروت قد طبعت/خصصت سابقاً لنقطة البيع نفسها. إعادة الطباعة تنشئ سجل عملية وعناصر طباعة جديداً، لكنها لا تنشئ حركات مخزون ولا تضيف قيمة مالية مرة أخرى.

### السجلات
- `print_jobs`: رأس كل عملية طباعة.
- `print_job_items`: لقطة تاريخية من بيانات كل كرت ضمن العملية.
- `pos_inventory_movements`: حركات التخصيص التجارية، مرة واحدة لكل كرت.
- `card_events`: أحداث الطباعة والتخصيص وإعادة الطباعة.

واجهة الطباعة الحالية تعرض معاينة قسائم قابلة للطباعة من المتصفح بعد تسجيل العملية. إنشاء PDF مستقل ومحرر القوالب المتقدم ما زالا ضمن التطوير التالي.


### إدارة نقاط البيع

- `GET /api/v1/points-of-sale`: عرض نقاط البيع المفعلة.
- `GET /api/v1/points-of-sale?include_inactive=true`: عرض جميع النقاط.
- `POST /api/v1/points-of-sale`: إنشاء نقطة بيع.
- `PATCH /api/v1/points-of-sale/{point_id}`: تعديل بيانات نقطة البيع أو إيقافها.

مثال الإنشاء:

```json
{
  "code": "SHOP-01",
  "name": "نقطة السوق",
  "contact_name": "المسؤول",
  "phone": "700000000"
}
```

### ملخص مخزون نقطة البيع

`GET /api/v1/points-of-sale/{point_id}/inventory`

يعرض عدد الكروت المخصصة والمستخدمة والموقوفة، والقيمة التجارية التي تم تخصيصها بالطباعة، وعدد الكروت المجانية المطبوعة. القيمة التجارية لا تتضاعف عند إعادة الطباعة.


### سجل الطباعة وإعادة الطباعة

`GET /api/v1/print-jobs?point_of_sale_id=1&limit=30`

يعرض آخر عمليات الطباعة لنقطة البيع مع أرقام الكروت وأسماء المستخدمين فقط، ولا يعيد كلمات المرور. استخدم `card_id` من سجل العملية لإرسال طلب إعادة الطباعة إلى `POST /api/v1/print-jobs` مع `is_reprint: true` ومفتاح جديد. استجابة الطباعة نفسها لا تُخزّن مؤقتاً، وتحتوي بيانات الاعتماد اللازمة للمعاينة والطباعة الفعلية.
